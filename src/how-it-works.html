Как из одного цвета получается палитра

Берём исходный цвет. Для светлых оттенков смешиваем его с белым, для тёмных — с чёрным. Пропорции одинаковые для всех цветных шкал.

Что означает APTS-MB-5

APTS — название проекта. MB — мобильная палитра. 5 — номер версии нашего алгоритма. Это наше обозначение, не общепринятый стандарт и не значение цвета.

В версии 5 используется одна таблица пропорций для всех генерируемых цветов. Если меняем правила расчёта — меняем версию, чтобы разработка понимала, по каким правилам получен результат.

1. Выбираем исходный цвет — это шаг 500

Например, mb-correct = #21C45D. Это зелёный, который мы сохраняем без изменений как mb-correct-500.

HEX — запись трёх каналов: красного, зелёного и синего. В нашем примере 21 → 33, C4 → 196, 5D → 93. Получается RGB (33, 196, 93). Значение каждого канала — от 0 до 255.

Числа 50, 100, 200…900 — только названия шагов: меньше 500 — светлее базы, больше 500 — темнее. Например, 400 не означает «40%».

2. Для каждого шага берём свой рецепт

Таблица показывает, сколько исходного цвета и сколько белого или чёрного смешать. Каждый оттенок считаем сразу от базы 500, а не от предыдущего оттенка.

Откуда эти доли? Они подобраны по исходным шкалам и принятому визуальному результату. Это постоянная таблица рецептов: её не подбираем заново под каждый цвет. Номер шага сам по себе не позволяет вычислить долю.

3. Пример: получаем зелёный 400

Для шага 400 берём 61,7325% исходного зелёного + 38,2675% белого. У белого RGB (255, 255, 255). Смешиваем каждый канал отдельно и округляем до целого:

Красный: 33 × 0,617325 + 255 × 0,382675 = 117,95385 → 118 Зелёный: 196 × 0,617325 + 255 × 0,382675 = 218,577825 → 219 Синий: 93 × 0,617325 + 255 × 0,382675 = 154,99335 → 155 RGB (118, 219, 155) → HEX #76DB9B → mb-correct-400

Для тёмного шага всё так же, только вместо белого используем чёрный (0, 0, 0). Например, 600 — это 81,5154% базы + 18,4846% чёрного.

Что происходит с другими цветами

У фиолетового, синего, красного, жёлтого и зелёного один расчёт и одна таблица. Брендовый mb-secondary тоже может быть зелёным или любым другим: меняем его базовый HEX, и вся его шкала пересчитывается. При одинаковой базе результат будет одинаковым независимо от названия переменной.

Исключения: mb-neutral хранится готовой шкалой. Переменные из блока «Без растяжки», включая mb-background, сохраняем как есть. Прозрачные overlay — отдельные доли прозрачности, не результат этой формулы.

Точная формула для разработки

Расчёт ведётся прямо по каналам sRGB 0–255. Чтобы одинаково округлять на Web, iOS и Android, храним долю целым числом: 61,7325% → k = 617325 при знаменателе D = 1000000.

C = floor((T × (D − k) + B × k + D / 2) / D) B — канал исходного цвета (0…255) T — 255 для светлых шагов, 0 для тёмных k — доля базы из общей таблицы, умноженная на D C — канал результата; floor — отбросить дробную часть

D / 2 перед делением даёт округление до ближайшего целого, а при ровно половине — вверх. Миллион — точность записи коэффициентов, а не значение цветового канала. Шаг 500 возвращает исходный цвет.

Формула вычисляет RGB непрозрачного цвета. Для Android #76DB9B записывается как #FF76DB9B: первые FF — полная непрозрачность, остальные шесть цифр — тот же цвет. В Compose сравниваем toArgb(), а не 64-битный Color.value.

Готовые реализации — во вкладке «Исходный код». Сверить свои значения RGB, Android ARGB или ColorInt можно во вкладке «Проверка HEX».
